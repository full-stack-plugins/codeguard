# P3C/PMD 原生组合与报告解析的局部验收（2026-09-24）

阿里巴巴 [P3C-PMD README](https://github.com/alibaba/p3c/blob/master/p3c-pmd/README.md) 当前给出 `com.alibaba.p3c:p3c-pmd:2.1.1`，说明规则实现基于 PMD。其 [POM](https://github.com/alibaba/p3c/blob/master/p3c-pmd/pom.xml) 将 `pmd.version` 设为 `6.15.0`，但同一 POM 的 Maven PMD 插件 `3.11.0` 运行配置仍依赖 P3C `2.0.1`。[Maven PMD 插件 3.11.0 的依赖表](https://maven.apache.org/plugins-archives/maven-pmd-plugin-3.11.0/dependencies.html)显示其默认 PMD 为 `6.8.0`；[官方覆盖说明](https://maven.apache.org/components/plugins-archives/maven-pmd-plugin-3.11.0/examples/upgrading-PMD-at-runtime.html)允许显式覆盖 PMD 版本，但兼容性需要验证。这些资料不能共同证明 `P3C 2.1.1 + Maven PMD 3.11.0 + PMD 6.15.0 + JDK 17/26` 已可运行。

Maven 的 [PMD 原生文档](https://maven.apache.org/plugins/maven-pmd-plugin/pmd-mojo.html)说明 `pmd:pmd` 会生成 XML 检查报告，`pmd:check` 使用报告做违规判断。Rust `pmd_xml` 适配器现只解析这类原生 XML：限制大小与节点数，拒绝 DTD、非 UTF-8、错误命名空间、版本不符及非法位置；原生处理错误使报告 incomplete，同时保留可验证的违规。规则集显示名不能证明官方 P3C 已加载；空 XML 仅是结构有效，不能满足 lint 义务。测试使用明确标为 `Fixture Rules` 的合成报告，不冒充 P3C 真工具验收。

报告里出现 `suppressedviolation` 时，当前适配器保持已解析违规并返回 `native_suppression_requires_policy_review`，不能让原生 suppression 静默消掉必需义务。没有输出 suppression 节点也不能据此断言不存在 suppression；真实执行必须锁定原生报告配置并复核项目配置与批准政策。

原生调用还有独立的假通过风险：[Maven PMD 插件 3.11.0 的实现](https://maven.apache.org/components/plugins-archives/maven-pmd-plugin-3.11.0/xref/org/apache/maven/plugins/pmd/PmdReport.html)默认规则集为 `/rulesets/java/maven-pmd-plugin-default.xml`，`pmd.skipPmdError` 默认 `true`，并允许 `pmd.skip`、排除文件、优先级阈值和分析缓存。因而 Maven 退出 0、生成空 XML 或 XML 中没有 `<error>`，均不足以证明官方 P3C 执行完整。后续原生命令验收须核对生效规则集来自受信 P3C 制品、处理错误不会被忽略、跳过/排除/阈值/缓存配置与批准政策一致，并以独立执行范围证据证明已扫描目标。上述要求不能靠 Rust XML 解析器推断。报告必须在本次隔离运行区新生成，读入时核对来源与快照；既有 `target/pmd.xml` 不能作为本轮证据。

已准备原生规则加载哨兵：`tests/fixtures/p3c_native/violating/Bad_Name.java` 与 `tests/fixtures/p3c_native/clean/GoodName.java`。阿里官方 [命名规则集](https://github.com/alibaba/p3c/blob/master/p3c-pmd/src/main/resources/rulesets/java/ali-naming.xml)声明 `ClassNamingShouldBeCamelRule`，其[规则实现](https://github.com/alibaba/p3c/blob/master/p3c-pmd/src/main/java/com/alibaba/p3c/pmd/lang/java/rule/naming/ClassNamingShouldBeCamelRule.java)使用 UpperCamelCase 正则；因此前者预期命中、后者预期不命中。可复跑的 Maven 原生项目配置见 `tests/fixtures/p3c_native/pom.xml`，Rust 验收调用见 `crates/codeguard-cli/tests/p3c_native_replay.rs`。

2026-09-24 本机已实际解析 `p3c-pmd:2.1.1`、`maven-pmd-plugin:3.11.0`、显式 `pmd-core/pmd-java:6.15.0`；本机 Maven 仓库标记显示 P3C JAR 是通过 `nexus-aliyun` 镜像取得，不能把该缓存记录称为直接从 Maven Central 下载。在全新临时项目中，JDK 8.0.504、17.0.20.1、21.0.12.1 和 26.0.1 的四次 Rust 验收均通过：违规文件的原生 XML 声明 PMD `6.15.0`，报告 `ClassNamingShouldBeCamelRule` / `AlibabaJavaNaming`，路径与输入文件一致；干净文件无诊断；不存在的规则集令 Maven 非零退出。JAR 中也存在 `rulesets/java/ali-naming.xml` 与 `ClassNamingShouldBeCamelRule.class`，生成的 `target/ali-naming.xml` 引用该类。这是**该哨兵在这四个本机 JDK 上实际加载规则**的证据，不推广为全部规则或所有项目/JDK 的兼容性证明。[阿里 P3C 仓库](https://github.com/alibaba/p3c/blob/master/p3c-pmd/README.md)与 [Maven Central POM](https://central.sonatype.com/artifact/com.alibaba.p3c/p3c-pmd/2.1.1)提供版本对照。

进一步将 Maven 插件及其依赖放进单独的约 26 MiB 本地仓库（524 个文件），使用 `tests/fixtures/p3c_native/settings.xml` 隔离用户 settings。Rust 验收固定 `-o`、全限定插件目标和 `-Dmaven.repo.local=<隔离仓库>`，执行前及每个样本后核对整个仓库的 `codeguard-bundle-tree-v1` 摘要。本机目录树观测值为 `587618cd1f2813bfe0c4a11c6ec167522ae61095abbdf2c060c3621bb6e13879`；JDK 8/17/21/26 的离线正反例再次全部通过且摘要不变。`pmd:pmd` 短名前缀在隔离 settings 中无法离线解析，因此验收改用 `org.apache.maven.plugins:maven-pmd-plugin:3.11.0:pmd`。这证明该隔离仓库足够支持**当前哨兵**离线运行，不表示完整发行供应链已有批准来源。

复跑命令：`CODEGUARD_MAVEN_BIN=/opt/homebrew/bin/mvn CODEGUARD_JAVA_HOME=<JDK_HOME> CODEGUARD_P3C_MAVEN_REPO=<隔离仓库绝对路径> CODEGUARD_P3C_REPO_TREE_SHA256=587618cd1f2813bfe0c4a11c6ec167522ae61095abbdf2c060c3621bb6e13879 cargo test -p codeguard-cli --test p3c_native_replay --offline -- --ignored`。`--offline` 限制 Cargo，Rust 测试的 Maven 参数另行包含 `-o`。本机记录的主要 JAR SHA-256：Maven PMD 3.11.0 `2b1c95ea99654b466e111a1a613a9a1d7abbea37951a703a43cd9ed6e9f60d66`，P3C 2.1.1 `e7afec9340a0f30f56f4fdcd3b9c49e79ed24253719fcb9f457f5bcb43e54860`，PMD core 6.15.0 `776c6315798e58cc362abba33b69fc074f7a25673706ddc6355cdbd54dc1f572`，PMD Java 6.15.0 `3a7d4f8c6054c46cc0954dc34fa28d627d827906f1a183fa98fcdaeb26a574fa`。仓库树摘要和单体摘要都是本机观测值；工具锁仍须接纳并验证它们，再结合批准来源和 JDK 身份。

真实输出揭示两个门禁细节：`pmd:pmd` 即使报告违规仍以 0 退出，因此不能套用 PMD 直接 CLI 的退出 4 契约；干净 XML 没有 `<file>` 节点，因此空报告不能单独证明目标文件已扫描。后续仍须把离线仓库闭包纳入正式工具锁、核对生效配置和源集覆盖、把运行接入正式 `codeguard check`、防范旧报告与处理错误，并验证直接 PMD CLI/JDK 组合。OpenSpec 6.2 暂不勾选。
